{# Makes a wide list table reachable. Included by brand/list_table.html, which is the root of the brand list-template chain - AuditLogAdmin's `list_template` directly, and AuditedModelView's through brand/model_list.html, which brand/staff_list.html and brand/ip_block_list.html extend in turn. So this reaches all seventeen ModelView list pages in the panel and no other screen; that is asserted, page by page, in tests/admin/test_list_table.py. THE DEFECT. sqladmin already wraps its list table in `
`, and Tabler already gives that `overflow-x: auto`, so the div is a horizontal scroll container and always was. What it never had was a HEIGHT. The div is as tall as the table, and a page of 100 rows is 4656px tall - so the horizontal scrollbar, which a browser draws at the BOTTOM INSIDE EDGE of the scroll container, is drawn 4656px down the page. Measured in Chromium at 1280x900 on /admin/factor-upstream/list with the ReFED set loaded: the container's top is at y=783 and its scrollbar therefore sits at y~5424, about 4500px below the fold. The content is reachable by shift+wheel and by nothing a reader can see, which is why the report was "cannot scroll sideways" rather than "the scrollbar is inconvenient" - an affordance nobody can find is not an affordance. The NZ taxonomy hid this. Its widest list is 965px against a 682px container, so the two right-hand columns were clipped and nobody chased them. The ReFED comparison set makes the same table 2187px wide against the same 682px, and its codes are long enough (`refed_foodservice_breads_bakery - ReFED Foodservice / Breads & Bakery`) that a row ends mid-word. The bug is not new; the data that shows it is. THE FIX, in one sentence: give the container a height, so that the scrollbar it already had is drawn somewhere a person can see it, and pin the header row to the top of the box it now has. `vh` and not a pixel count, because the load-bearing property is that the whole scrollport - including its bottom edge, including its horizontal scrollbar - fits on screen at once once the reader has scrolled the table into view. A fixed 600px does not have that property on a laptop in a video call. WHAT THIS DELIBERATELY DOES NOT DO is trap the page. `overscroll-behavior` is set on the X AXIS ONLY: a horizontal flick that runs off the end of the table stops there instead of being handed to the browser as a back-gesture, which is a real hazard on a precision trackpad over a table this wide. Vertical overscroll is left at `auto` on purpose, so a wheel that reaches the last row carries on scrolling the page, exactly as it does over any other part of it. A table that swallowed the page's vertical scroll would be a worse defect than the one being fixed here. #}
