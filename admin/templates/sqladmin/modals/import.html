{# sqladmin's import modal, unchanged, plus this panel's CSRF token. THE ORIGINAL IS INCLUDED, NOT COPIED. `sqladmin_original` is a prefix loader sqladmin registers for exactly this (`Admin.init_templating_engine`), so the ninety lines of modal markup - the file input, the progress bar, the result modal and every translated string in them - stay sqladmin's and cannot go stale here. The same rule admin/templates/sqladmin/layout.html follows, and the one admin/modelviews.py's `described()` gives the argument for: a forked template is somebody else's code that rots silently at the next upgrade. WHY THE TOKEN IS HERE RATHER THAN INSIDE THE FORM. sqladmin's own `statics/js/main.js` does not serialise the form. It builds a `FormData` by hand: const formData = new FormData(); formData.append('csvfile', file); formData.append('continue_on_error', ...); so a hidden `` inside that form would be in the DOM and in no request. The field is carried to the request by /admin/static/import-csrf.js instead, which reads it from here. It stays a real form field in the POST, which is what admin/importing.py checks and what every other form in this panel sends. This modal renders only where `can_import` is true, which on this panel is an administrator on one of the fourteen importable screens — seven taxonomy, the five children of a factor set, and the two comparison- scenario tables (admin/importing.py, contract §8.1.1). #} {% include "sqladmin_original/modals/import.html" %} {# KEEPING A REFUSAL READABLE ONCE IT IS IN THE PAGE. When the import route answers anything other than 200, sqladmin's own `main.js` reads the body as text and puts it into `#modal-import-text` with jQuery's `.text()`: const message = await response.text(); throw new Error(message || 'An error occurred while importing CSV.'); ... $('#modal-import-text').text(error.message); `.text()` sets `textContent`, so the newlines survive into the DOM and then collapse on screen under the browser's default `white-space: normal`. That is fine for sqladmin's own one-line errors and wrong for this panel's: admin/importing.py refuses a file by naming *every* value it could not read, one per line, and a staff member looking at four of those run together into a single paragraph has been handed the wall of text the messages were written to avoid. `pre-wrap` rather than `pre-line`: it keeps the two-space indent that sets each refusal off from the next, and still wraps a long line to the width of the dialog. Scoped to the one element, so nothing else sqladmin renders changes. #} {# THE MODE CONTROL, AND WHY IT IS OUT HERE RATHER THAN IN THE FORM. Same reason as the token above: the original modal is *included*, not copied, so there is nowhere inside it to write a field without forking ninety lines of somebody else's markup. /admin/static/import-csrf.js moves this block into the dialog and puts its value into the upload, exactly as it does for the token. THE WORDING IS THE POINT. `model_view.import_retirement_word` is "deactivated" on the nine tables that carry an `active` column and "deleted" on the five that do not (admin/importing.py's `retirement_for`), so the option says what this screen will actually do. A control labelled "delete rows not in the file" on a table where nothing is deleted, or "deactivate" on one where the rows are gone for good, is the panel telling a staff member something false about an act with no undo. WP4 REPLACES THIS MODAL and will draw the control properly, with the preview that admin/importing.py's dry run already computes. Nothing here is meant to survive that. #}
