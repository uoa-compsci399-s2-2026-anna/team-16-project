{# /admin/submissions/details/{id} - the drill-down. THE POINT OF THIS FILE. sqladmin's own details table renders a relationship as a list of `__str__` values, so `entries` would print as a row of "processing / bread and bakery" links and the LINES - the destinations and the kilograms, which is the whole of what a calculation actually says - would not appear at all. `SubmissionLine` is not a registered view either, so there is nothing to click through to. Hence: sqladmin's table above via `{{ super() }}` for the submission's own fields, and the tree below for the two levels underneath it. WHAT IS NOT HERE, AND WHY. No token, no address, no user agent, no fingerprint - none of the last three was ever collected (contract §2.3), and `token` is deliberately absent from `column_details_list` so that a live de-duplication token never renders on a page one click from every row. See admin/submission_views.py's module docstring. PREVENTION IS LABELLED RATHER THAN LEFT TO READ AS A DESTINATION. §4.1's `prevention` is a destination whose factors are all zero - it is how "we would waste less" is expressed while keeping both scenarios mass-conserving. On this page it is the difference between "they said they would send 300 kg to compost" and "they said 300 kg would not be waste at all", which a reader should not have to know the taxonomy to see. Both scenarios are shown, side by side per entry, because the alternative is half of what was submitted (§4.1) and a page that showed only the current scenario would be describing a comparison by one of its two sides. An entry with no alternative is the ordinary case - the main calculator flow sends `alternative: null` - and says so rather than rendering an empty column. #} {% extends "sqladmin/details.html" %} {% block details_table %} {{ super() }}
