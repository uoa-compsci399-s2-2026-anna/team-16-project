This copy is only correct against the sqladmin it was taken from, and "the sqladmin it was taken from" means the version pinned in docker/constraints.txt - the one the images build and the one CI installs. Not whatever a developer's machine happens to have. WHY THIS FILE IS COPIED RATHER THAN EXTENDED. Jinja can override a block; it cannot override a macro. Every translatable string below sits inside a macro, so `{% extends "sqladmin_original/_macros.html" %}` reaches none of them. Shadowing the file is the only seam there is - sqladmin's loader looks in this panel's templates_dir before its own package (`Admin.init_templating_engine`), the same mechanism that already replaces sqladmin/index.html and sqladmin/login.html. WHAT IT BUYS. Three things that have no other render-time hook: * `field.description` - all 82 field help texts, on every create and edit form in the panel; * `menu.display_name` - the left-hand navigation, whose labels are baked into sqladmin's Menu at start-up and so cannot be translated per request anywhere else; * the required-field tooltip. WHAT SHADOWING COSTS, which the 0.30.0 -> 0.31.0 move made concrete. A copy does not merely go stale, it SUPPRESSES the original. 0.31.0 added `data-sqladmin-menu-category` here and JS in sqladmin/statics/js/main.js that remembers which navigation categories a staff member left open; 0.31.0 also dropped the `show` class that had pinned every category open unconditionally. While this file still carried 0.30.0's markup, the panel shipped on 0.31.0 rendered 0.30.0's always-open menu and that new JS matched no element and did nothing - no error, nothing in a log. Anything sqladmin adds to these macros has to be pulled through here by hand. THE DRIFT RISK, AND WHAT HOLDS IT. tests/admin/test_i18n.py::test_the_vendored_macros_copy_still_matches_its_original compares this file against the installed one with the `_()` calls stripped back out, so an upgrade that edits the original fails the suite instead of quietly reverting a translation.
