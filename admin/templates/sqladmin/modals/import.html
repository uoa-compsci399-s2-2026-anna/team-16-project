THIS FILE REPLACES SQLADMIN'S OWN MODAL RATHER THAN INCLUDING IT, AND THAT IS A CHANGE FROM WHAT STOOD HERE. Until WP4 this template was `{% include "sqladmin_original/modals/import.html" %}` plus three patches around it, on the rule this project follows everywhere else: reach a template, do not fork it. The rule has not changed and neither has the reason — a copied template is somebody else's code that rots silently at the next upgrade — but three of the things this dialog has to do cannot be reached from outside the markup: * **the CSRF token has to be in the request.** sqladmin's own `statics/js/main.js` builds the upload's `FormData` by hand and never serialises the form, so a hidden `` inside its form is in the DOM and in no request. WP1 carried the field past that by replacing `window.fetch` for the duration of one call. It said this modal's replacement would delete that wrapper, and it does: /admin/static/import.js builds its own body and puts the token in it, which is what every other form in this panel does. * **both formats in one dialog.** The shipped input is `accept="text/csv"` and the shipped heading says "Import CSV". This screen takes `.csv` and `.json` on one path (admin/importing.py). * **drag-and-drop.** `dragover`, `drop` and `dragenter` appear zero times in what sqladmin ships; it is a plain ``. NOTHING OF SQLADMIN'S IS COPIED HERE. This is not a fork of that file — it is different markup for a different dialog, and every line of `sqladmin/_import.py` (619 of them: the CSV parsing, the per-row validation, the count check, the streaming response) still runs on the server exactly as before. What changed is the browser half, which is the half sqladmin could not know this panel's rules about. THE OUTER `id="modal-import"` IS KEPT deliberately. sqladmin's own list page renders the Import button with `data-bs-target="#modal-import"`, so keeping the id means the button still opens this dialog without the list template being touched. sqladmin's `main.js` also binds a few handlers at `#modal-import-form`, `#modal-import-text` and `#modal-import-progress` — none of which exist below, so jQuery matches an empty set and they do nothing. That is the point: its submit handler never fires, because there is no `#modal-import-form` for it to fire on. THIS DIALOG RENDERS ONLY WHERE `can_import` IS TRUE, which on this panel is an administrator on one of the fourteen importable screens — seven taxonomy, the five children of a factor set, and the two comparison- scenario tables (admin/importing.py, contract §8.1.1). #}

{# WHAT A .JSON FILE HAS TO LOOK LIKE, AND WHY IT IS SPELT OUT HERE. The hint above says a file is "written the way this screen's own Export writes one", which is true and is not enough to write one from scratch - and JSON is the format a staff member is most likely to open in an editor and change by hand. EVERY RULE BELOW IS READ OUT OF admin/importing.py, not composed from what the format ought to be: * array of objects, refused by shape, naming what was found - `rows_from_json` / `_json_is_not_a_list`; * every import column present in every object - `rows_from_json`'s `missing` check, which is STRICTER than "the keys are the import columns": a column left out is a refusal, not a blank; * one value per cell, `null` for a blank - `_json_cell`; * UTF-8 with a tolerated BOM - `content.decode("utf-8-sig")`; * line numbers from 2 - `line = index + 2`, and JSON_LINE_NOTE, which is the sentence the server itself adds to a refusal; * foreign keys by natural key - `natural_key_column` and `_unknown_code`, and `_NATURAL_KEY_COLUMNS` for why a factor set is named by its version label; * the upsert matches on the row's own natural key - MODE_UPSERT and `_key_cells`. THE CSV RULES ARE NOT RESTATED. This is the JSON format only. `

{# THE PREVIEW. Filled from the dry run's own JSON — every count and every line number in it was computed by the code that would do the writing (admin/importing.py's `build_import_plan`), not by the browser. `role="status"` rather than `role="alert"`: it is the answer to something the visitor asked for, not an interruption. #} {# THE SCRIPT'S OWN STRINGS LIVE HERE, on the element each belongs to, read back with `getAttribute`. That is `security.js`'s pattern and this panel's established one, and the alternative - a second mechanism, a JSON blob of strings or a `_()` reachable from JavaScript - would be a second place to look for a sentence. THE FOUR PREVIEW HEADINGS SURVIVE A MODE CHANGE because all four are rendered here, once, whatever the mode is. The mode decides which LISTS the server's plan carries, not which labels exist; a mode changed in the browser therefore needs no reload and no second request to have its heading, and `forgetThePreview` empties the element's children without touching its attributes. `{count}`, `{key}` and `{line}` rather than `%(count)s`: these are substituted by the script, and jinja2's newstyle `_()` applies `translated % variables` to every string it returns - so a `%()s` left for later raises KeyError at render time. Measured, not feared. #}
